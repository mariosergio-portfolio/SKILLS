# Oracle Database — DDL Good Practices & Design Reference

## When to use this skill
Activate when the user types `/tech-database-oracle` or asks about designing or reviewing an Oracle database schema, writing DDL scripts, choosing the right data types, defining constraints, or leveraging Oracle-specific features.

---

## General DDL Principles

- **Schema migrations over manual DDL** — always manage DDL through a versioned migration tool (Flyway, Liquibase). Never apply raw DDL directly to a production database outside a migration pipeline.
- **One concern per migration file** — each migration adds, alters, or drops exactly one logical unit (one table, one index batch, one constraint). Never bundle unrelated changes.
- **Immutable migrations** — once a migration is applied to any environment, never edit it. Add a new migration to correct mistakes.
- **Never use `DROP … CASCADE CONSTRAINTS` in production migrations** — be explicit about what is dropped.
- **DDL is auto-committed in Oracle** — Oracle DDL statements issue an implicit COMMIT before and after execution; there is no transactional DDL rollback. Design migrations so each step is independently safe.

## Naming Conventions

| Object | Convention | Example |
|--------|-----------|---------|
| Table | `SNAKE_CASE`, plural | `ORDER_ITEMS`, `CUSTOMER_ADDRESSES` |
| Column | `SNAKE_CASE` | `CREATED_AT`, `UNIT_PRICE` |
| Primary key constraint | `PK_<TABLE>` | `PK_ORDER_ITEMS` |
| Foreign key constraint | `FK_<TABLE>_<REFERENCED_TABLE>` | `FK_ORDER_ITEMS_ORDERS` |
| Unique constraint | `UQ_<TABLE>_<COLUMNS>` | `UQ_CUSTOMERS_EMAIL` |
| Check constraint | `CK_<TABLE>_<RULE>` | `CK_PRODUCTS_PRICE_POSITIVE` |
| Index | `IDX_<TABLE>_<COLUMNS>` | `IDX_ORDERS_CUSTOMER_ID` |
| Function-based index | `IDX_<TABLE>_<EXPRESSION>` | `IDX_CUSTOMERS_EMAIL_UPPER` |
| Sequence | `SEQ_<TABLE>_<COLUMN>` | `SEQ_INVOICES_NUMBER` |
| Trigger | `TRG_<TABLE>_<EVENT>` | `TRG_PRODUCTS_SET_UPDATED_AT` |
| View | `VW_<NAME>` | `VW_ACTIVE_PRODUCTS` |
| Materialized view | `MV_<NAME>` | `MV_ORDER_SUMMARY` |
| Package | `PKG_<DOMAIN>` | `PKG_ORDER_MANAGEMENT` |
| Procedure | `PRC_<ACTION>_<ENTITY>` | `PRC_ARCHIVE_OLD_ORDERS` |
| Function | `FN_<ACTION>_<ENTITY>` | `FN_CALC_ORDER_TOTAL` |

> Use **explicit constraint names** on every constraint — never rely on Oracle auto-generated names (e.g. `SYS_C007654`). Explicit names make error messages readable and allow targeted `ALTER TABLE … DROP CONSTRAINT`.

> Oracle identifiers are **case-insensitive by default** and stored in UPPERCASE. Use `SNAKE_CASE` consistently and avoid quoted identifiers (`"myColumn"`) unless absolutely necessary — quoted identifiers are case-sensitive and a maintenance burden.

## Primary Keys

### RAW(16) / SYS_GUID() — UUID equivalent (preferred for distributed / API-exposed IDs)
```sql
ID RAW(16) DEFAULT SYS_GUID() NOT NULL,
CONSTRAINT PK_ORDERS PRIMARY KEY (ID)
```
- `SYS_GUID()` generates a 16-byte globally unique identifier — Oracle's UUID equivalent.
- Never expose sequential integers as public API identifiers.
- Use `RAW(16)` for all tables that communicate IDs to clients or external systems.

### NUMBER GENERATED AS IDENTITY — surrogate sequential PK (preferred for high-volume internal/audit tables)
```sql
ID NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```
- `GENERATED ALWAYS AS IDENTITY` (Oracle 12c+) is the standard SQL syntax — prefer it over the legacy `SEQUENCE` + `DEFAULT` pattern.
- Suitable for append-only logs, audit trails, and internal join tables.
- Use `GENERATED BY DEFAULT AS IDENTITY` when you need to insert explicit values (e.g. data migration).

## Data Types — Choosing the Right One

| Use case | Recommended type | Avoid |
|----------|-----------------|-------|
| Monetary / financial amounts | `NUMBER(19,4)` | `FLOAT`, `BINARY_FLOAT`, `BINARY_DOUBLE` — rounding errors |
| Percentage / rate | `NUMBER(5,4)` (e.g. 0.1750 = 17.50 %) | `FLOAT` |
| Short enumerated value | `VARCHAR2(30)` + CHECK | `CHAR` with padding issues |
| Timestamps (UTC, with time zone) | `TIMESTAMP WITH TIME ZONE` | `DATE` (no sub-second precision, no tz) |
| Timestamps (UTC, no tz conversion) | `TIMESTAMP` with app-enforced UTC | `DATE` for anything needing sub-second precision |
| Date only | `DATE` (time portion zeroed) | `TIMESTAMP` when time is irrelevant |
| Boolean flags | `NUMBER(1)` + CHECK (`IN (0,1)`) | No native BOOLEAN in SQL DDL (PL/SQL only) |
| Short bounded string | `VARCHAR2(n)` | `CHAR(n)` — padded with spaces, comparison pitfalls |
| Free text, long content | `CLOB` | `VARCHAR2` > 4000 bytes (hard limit) |
| Binary data | `BLOB` | `RAW` for data > 2000 bytes |
| Semi-structured / JSON (Oracle 21c+) | `JSON` type | `CLOB` for JSON — no native querying |
| Semi-structured / JSON (Oracle 12c–19c) | `CLOB` + `IS JSON` CHECK + JSON indexes | `VARCHAR2` — size limit |
| XML documents | `XMLTYPE` | `CLOB` — no XPath/XQuery support |
| Currency code | `CHAR(3)` (ISO 4217) | free `VARCHAR2` |
| Country / language code | `CHAR(2)` or `VARCHAR2(5)` | free `VARCHAR2` |

> Oracle `DATE` stores both date **and** time (hour, minute, second) — it is **not** a pure date type. To store date-only values, always zero the time component or use a CHECK constraint. Use `TIMESTAMP` for sub-second precision.

## Constraints

### NOT NULL
Apply `NOT NULL` to every column that must always have a value — make nullability a deliberate, documented choice.

```sql
FULL_NAME VARCHAR2(255) NOT NULL
```

### UNIQUE
```sql
-- single-column unique
CONSTRAINT UQ_CUSTOMERS_EMAIL UNIQUE (EMAIL)

-- multi-column unique
CONSTRAINT UQ_CART_ITEMS_CART_PRODUCT UNIQUE (CART_ID, PRODUCT_ID)
```
Always name UNIQUE constraints explicitly.

### CHECK
```sql
CONSTRAINT CK_PRODUCTS_PRICE_POSITIVE  CHECK (PRICE > 0),
CONSTRAINT CK_PRODUCTS_STOCK_NON_NEG   CHECK (STOCK_QUANTITY >= 0),
CONSTRAINT CK_ORDERS_STATUS            CHECK (STATUS IN ('PENDING','PAID','SHIPPED','DELIVERED','CANCELLED')),
CONSTRAINT CK_BOOLEAN_ACTIVE           CHECK (ACTIVE IN (0, 1))
```
- Use CHECK for domain invariants Oracle can enforce without a trigger.
- Prefer CHECK over application-only validation for critical business rules.
- Oracle evaluates CHECK constraints as `TRUE` or `UNKNOWN` (NULL passes) — use `NOT NULL` + CHECK together.

### FOREIGN KEY
```sql
CONSTRAINT FK_ORDER_ITEMS_ORDERS   FOREIGN KEY (ORDER_ID)   REFERENCES ORDERS(ID),
CONSTRAINT FK_ORDER_ITEMS_PRODUCTS FOREIGN KEY (PRODUCT_ID) REFERENCES PRODUCTS(ID)
```
- Always name FKs explicitly.
- Default action is `NO ACTION` (restrict) — prefer it unless a cascade is clearly required.
- Use `ON DELETE CASCADE` only for owned child entities.
- Use `ON DELETE SET NULL` for optional references.
- **Never** use `ON DELETE CASCADE` on financial or audit records.
- **Always create an index on every FK column** — Oracle does not auto-index FKs, and an un-indexed FK causes full table locks on parent DELETE/UPDATE.

## Sequences

```sql
-- Standalone sequence (pre-12c style or for business-visible numbers)
CREATE SEQUENCE SEQ_INVOICES_NUMBER
    START WITH 1000
    INCREMENT BY 1
    NOCYCLE
    NOCACHE;           -- or CACHE 20 for high-throughput tables

-- Use in INSERT
INSERT INTO INVOICES (ID, INVOICE_NUMBER, ...)
VALUES (SYS_GUID(), SEQ_INVOICES_NUMBER.NEXTVAL, ...);

-- Or as a column default (Oracle 12c+)
INVOICE_NUMBER NUMBER DEFAULT SEQ_INVOICES_NUMBER.NEXTVAL NOT NULL
```

- Use standalone sequences for business-visible sequential numbers (invoice numbers, order numbers).
- Use `GENERATED ALWAYS AS IDENTITY` for surrogate PKs — it is cleaner and SQL-standard.
- Use `CACHE` (e.g. `CACHE 20`) for high-throughput sequences; gaps are acceptable in exchange for performance.
- `NOCACHE` guarantees no gaps but serialises sequence generation — use only when gap-free is a hard requirement.

## Triggers

### Auto-updating `UPDATED_AT`

```sql
CREATE OR REPLACE TRIGGER TRG_PRODUCTS_SET_UPDATED_AT
    BEFORE UPDATE ON PRODUCTS
    FOR EACH ROW
BEGIN
    :NEW.UPDATED_AT := SYSTIMESTAMP;
END;
/
```

- Use `SYSTIMESTAMP` for sub-second precision (`TIMESTAMP WITH TIME ZONE`); use `SYSDATE` for `DATE` columns.
- Always use `BEFORE` row triggers for setting audit columns — the value must be set before the row is written.
- Use `CREATE OR REPLACE TRIGGER` so migrations are idempotent.

### Auto-populating PK from sequence (pre-12c pattern)

```sql
CREATE OR REPLACE TRIGGER TRG_ORDERS_PK
    BEFORE INSERT ON ORDERS
    FOR EACH ROW
    WHEN (NEW.ID IS NULL)
BEGIN
    :NEW.ID := SYS_GUID();
END;
/
```

> Prefer `DEFAULT SYS_GUID()` on the column definition (Oracle 12c+) over a trigger — it is simpler and avoids trigger overhead.

## Timestamps & Timezone Handling

```sql
-- Preferred: store with time zone so Oracle normalises to UTC on storage
CREATED_AT TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL,
UPDATED_AT TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL
```

- Always store timestamps in **UTC**.
- `TIMESTAMP WITH TIME ZONE` stores the offset alongside the value — use `AT TIME ZONE 'UTC'` when reading if normalisation is needed.
- `TIMESTAMP WITH LOCAL TIME ZONE` stores in the database timezone and converts to the session timezone on read — useful for single-timezone deployments.
- Use `SYSTIMESTAMP` for `TIMESTAMP` defaults; use `SYSDATE` only for `DATE` columns.
- Avoid mixing `DATE` and `TIMESTAMP` in the same schema — pick one and be consistent.

## Indexing Strategy

### Always index
- All foreign key columns (Oracle does not auto-index FKs — an un-indexed FK on the child table causes row-level locks on the parent during DELETE/UPDATE).
- Columns used in frequent `WHERE` filters (status, date ranges, category).
- Columns used in `ORDER BY` on large tables.
- Join columns in large tables.

### Function-based indexes
```sql
-- Case-insensitive email lookup
CREATE INDEX IDX_CUSTOMERS_EMAIL_UPPER
    ON CUSTOMERS (UPPER(EMAIL));

-- Query must use the same expression
SELECT * FROM CUSTOMERS WHERE UPPER(EMAIL) = UPPER(:email);
```
Use function-based indexes when queries always apply a function to the column (e.g. `UPPER`, `TRUNC`, `TO_CHAR`).

### Composite indexes — column order matters
```sql
-- Supports: WHERE CUSTOMER_ID = ? ORDER BY PLACED_AT DESC
CREATE INDEX IDX_ORDERS_CUSTOMER_PLACED
    ON ORDERS (CUSTOMER_ID, PLACED_AT DESC);
```
Put equality-filter columns first, range/sort columns last.

### Bitmap indexes
```sql
CREATE BITMAP INDEX IDX_ORDERS_STATUS_BMP
    ON ORDERS (STATUS);
```
- Use **only on data warehouse / read-heavy tables** with low-cardinality columns (e.g. status, gender, region).
- **Never use bitmap indexes on OLTP tables** — they cause severe lock contention on concurrent DML.

### Index types
| Type | Use case |
|------|---------|
| `BTREE` (default) | Equality, range, ORDER BY — general-purpose default |
| Function-based | Queries filtering on expressions or functions |
| Bitmap | DW/analytics, low-cardinality, read-only columns |
| `UNIQUE` | Enforces uniqueness + provides index |
| `INVISIBLE` | Test an index without the optimizer using it yet |
| `NOLOGGING` | Bulk load performance — skip redo log; rebuild after load |

### What NOT to index
- Columns with very low cardinality on OLTP tables (use bitmap on DW only).
- Columns that are never filtered, joined, or sorted.
- Every column "just in case" — index bloat slows DML and wastes storage.

## Partitioning

Use table partitioning for tables expected to grow beyond tens of millions of rows.

```sql
-- Range partition by month (audit logs, events, time-series)
CREATE TABLE AUDIT_LOGS (
    ID         RAW(16)          DEFAULT SYS_GUID() NOT NULL,
    EVENT_TYPE VARCHAR2(50)     NOT NULL,
    PAYLOAD    CLOB,
    CREATED_AT TIMESTAMP        DEFAULT SYSTIMESTAMP NOT NULL,
    CONSTRAINT PK_AUDIT_LOGS PRIMARY KEY (ID, CREATED_AT)
)
PARTITION BY RANGE (CREATED_AT) INTERVAL (NUMTOYMINTERVAL(1, 'MONTH'))
(
    PARTITION P_INITIAL VALUES LESS THAN (TIMESTAMP '2025-01-01 00:00:00')
);
```

- Use `INTERVAL` partitioning (Oracle 11g+) for time-series data — new partitions are created automatically.
- Use `LIST` partitioning for discrete values (e.g. region, status).
- Use `HASH` partitioning for even data distribution when no natural range or list exists.
- Use `COMPOSITE` partitioning (e.g. RANGE–LIST, RANGE–HASH) for multi-dimensional access patterns.
- Indexes on partitioned tables are **local** (per partition) or **global** — prefer local indexes unless a global index is required for uniqueness across partitions.
- Do **not** partition tables with fewer than ~5–10M rows — the overhead outweighs the benefit.

## JSON Support

### Oracle 21c+ — native JSON type
```sql
CREATE TABLE PRODUCT_ATTRIBUTES (
    ID         RAW(16)  DEFAULT SYS_GUID() NOT NULL,
    PRODUCT_ID RAW(16)  NOT NULL,
    ATTRIBUTES JSON     NOT NULL,
    CONSTRAINT PK_PRODUCT_ATTRIBUTES PRIMARY KEY (ID),
    CONSTRAINT FK_PROD_ATTRS_PRODUCTS FOREIGN KEY (PRODUCT_ID) REFERENCES PRODUCTS(ID)
);

-- JSON path query
SELECT P.ID, P.ATTRIBUTES.color
FROM   PRODUCT_ATTRIBUTES P
WHERE  P.ATTRIBUTES.size = 'M';
```

### Oracle 12c–19c — CLOB + IS JSON
```sql
CREATE TABLE PRODUCT_ATTRIBUTES (
    ID         RAW(16)  DEFAULT SYS_GUID() NOT NULL,
    PRODUCT_ID RAW(16)  NOT NULL,
    ATTRIBUTES CLOB,
    CONSTRAINT PK_PRODUCT_ATTRIBUTES PRIMARY KEY (ID),
    CONSTRAINT CK_ATTRIBUTES_IS_JSON CHECK (ATTRIBUTES IS JSON),
    CONSTRAINT FK_PROD_ATTRS_PRODUCTS FOREIGN KEY (PRODUCT_ID) REFERENCES PRODUCTS(ID)
);

-- JSON_VALUE / JSON_EXISTS queries
SELECT JSON_VALUE(ATTRIBUTES, '$.color') AS COLOR
FROM   PRODUCT_ATTRIBUTES
WHERE  JSON_EXISTS(ATTRIBUTES, '$.size?(@ == "M")');
```

**Use JSON when:**
- Attributes are sparse and vary by type (EAV pattern replacement).
- Schema is intentionally flexible and evolves per category.

**Do not use JSON when:**
- The same fields appear on every row — model them as proper columns.
- You need FK integrity or CHECK constraints on values inside the document.

## Optimistic Locking

```sql
VERSION_NUM NUMBER DEFAULT 0 NOT NULL
```

```sql
UPDATE PRODUCTS
SET    STOCK_QUANTITY = STOCK_QUANTITY - :delta,
       VERSION_NUM    = VERSION_NUM + 1,
       UPDATED_AT     = SYSTIMESTAMP
WHERE  ID          = :id
AND    VERSION_NUM  = :expected_version;
-- If SQL%ROWCOUNT = 0 → concurrent modification detected
```

- Add a `VERSION_NUM NUMBER DEFAULT 0 NOT NULL` column to any entity subject to concurrent updates.
- Check `SQL%ROWCOUNT` after the UPDATE — zero rows means an optimistic lock conflict.
- Pairs naturally with JPA `@Version` / EF Core concurrency tokens.

## Schemas / Users (Namespacing)

In Oracle, a **schema = user** — every user owns their own objects.

```sql
-- Create a schema (user) for a bounded context
CREATE USER catalog_schema IDENTIFIED BY "StrongPass1!"
    DEFAULT TABLESPACE users
    TEMPORARY TABLESPACE temp
    QUOTA UNLIMITED ON users;

-- Grant minimal privileges
GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE,
      CREATE TRIGGER, CREATE INDEX, CREATE VIEW TO catalog_schema;

-- Cross-schema reference (grant SELECT to another schema)
GRANT SELECT ON catalog_schema.PRODUCTS TO orders_schema;
```

- Use one Oracle schema per bounded context / microservice to enforce isolation.
- Cross-schema FKs are allowed via synonyms but introduce coupling — use them sparingly.
- Prefer **synonyms** (`CREATE SYNONYM`) over hard-coding `SCHEMA.TABLE` references in application queries.

## Common Anti-Patterns to Avoid

| Anti-pattern | Problem | Correct approach |
|-------------|---------|-----------------|
| Using `FLOAT` / `BINARY_DOUBLE` for money | Rounding errors in financial calculations | `NUMBER(19,4)` |
| Using `DATE` for timestamps | No sub-second precision, tz ambiguity | `TIMESTAMP WITH TIME ZONE` |
| No constraint names | Cryptic Oracle-generated names (`SYS_C007654`) | Always name every constraint |
| Un-indexed FK columns | Full table locks on parent DELETE/UPDATE | Index every FK column on the child table |
| Bitmap indexes on OLTP tables | Severe DML lock contention | Bitmap only for DW read-heavy tables |
| `CHAR(n)` for variable-length strings | Blank-padding causes subtle comparison bugs | `VARCHAR2(n)` |
| Quoted identifiers (`"myColumn"`) | Case-sensitive, maintenance burden | Plain unquoted UPPERCASE identifiers |
| `NULL` in CHECK constraints | NULL passes all CHECKs silently | Combine `NOT NULL` + `CHECK` |
| Storing JSON as plain `VARCHAR2` | Size limit (4000 bytes), no querying | `CLOB` + `IS JSON` or native `JSON` type (21c+) |
| `NOCACHE` sequences on high-throughput tables | Sequence bottleneck, serialised waits | `CACHE 20` or higher; gaps are acceptable |
| Business logic only in application code | DB can be inconsistent if accessed directly | Use CHECK, FK, and triggers for invariants the DB should own |
| Unbounded table growth without partitioning | Query degradation after millions of rows | Partition by range/interval; archive cold data |

## DDL Template — Canonical Table Structure

```sql
-- 1. Create table
CREATE TABLE <TABLE_NAME> (
    -- Primary key
    ID          RAW(16)                  DEFAULT SYS_GUID() NOT NULL,

    -- Business columns (NOT NULL first, nullable after)
    <COL_NAME>  <TYPE>                   NOT NULL,
    <COL_NAME>  <TYPE>,

    -- FK columns
    <FK_COL>    RAW(16)                  NOT NULL,

    -- Boolean flag example
    ACTIVE      NUMBER(1)  DEFAULT 1     NOT NULL,

    -- Audit timestamps
    CREATED_AT  TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL,
    UPDATED_AT  TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL,

    -- Named constraints
    CONSTRAINT PK_<TABLE>             PRIMARY KEY (ID),
    CONSTRAINT FK_<TABLE>_<REF>       FOREIGN KEY (<FK_COL>) REFERENCES <REF_TABLE>(ID),
    CONSTRAINT UQ_<TABLE>_<COLS>      UNIQUE (<COL1>, <COL2>),
    CONSTRAINT CK_<TABLE>_<RULE>      CHECK (<EXPRESSION>),
    CONSTRAINT CK_<TABLE>_ACTIVE      CHECK (ACTIVE IN (0, 1))
);

-- 2. Indexes (after table creation)
CREATE INDEX IDX_<TABLE>_<COL> ON <TABLE_NAME>(<COL>);

-- 3. UPDATED_AT trigger
CREATE OR REPLACE TRIGGER TRG_<TABLE>_SET_UPDATED_AT
    BEFORE UPDATE ON <TABLE_NAME>
    FOR EACH ROW
BEGIN
    :NEW.UPDATED_AT := SYSTIMESTAMP;
END;
/
```

## How to use this skill
1. Apply these Oracle DDL conventions and good practices to any schema design, migration script, or schema review task.
2. When writing DDL, always include explicit constraint names, choose the correct data type from the reference above, and add the canonical audit columns (`CREATED_AT`, `UPDATED_AT`).
3. When reviewing DDL, check against the anti-patterns table and the constraint naming rules.
4. Remember Oracle-specific rules: DDL is auto-committed, FKs are never auto-indexed, `DATE` includes time, and `BOOLEAN` is not available in SQL DDL.
5. Respond and assist in English unless the user requests another language.
6. Await further instructions from the user and execute them accordingly.
